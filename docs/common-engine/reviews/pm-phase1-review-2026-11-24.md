## A. 確認済みの良い設計方針

1. 旧コードを構造的な正解と仮定せず、既存の**承認済み動作**を比較基準とする。
2. Storyは宣言型パッケージをロードし、任意JS/HTML/CSS/コールバックを拒否する。
3. CommunicationとVocabulary Battleの判定は分離し、Speech I/Oは共有。
4. 置換完了時に旧エンジン経路を撤去し、Git blob不変の新規Story追加試験を設ける。
5. Productionを維持し、Save互換とiPhoneでの成功経路を移行比較基準とする。

## B. 実装前に必須の設計修正

### BLOCKER-01 — 「Storyごとのローカル仕様禁止」を**変更管理の規約**にする

**現状**: 設計書はStory ID条件分岐を除去すると記すが、将来「新機能が必要」となったとき、共通エンジンへのStory専用分岐を止める意思決定手順が未定義。

**変更要求**:
- Storyパッケージは**既存の共通機能カタログを組み合わせるだけ**であることをデータ契約に明記。
- カタログにない機能は、特定Storyの実装に着手する前に「共通機能提案 → 仕様/状態遷移/適用範囲 → 互換性/回帰テスト → 独立設計レビュー → ディレクター承認」を要する。
- 共通コードにStory番号、質問ID、素材パス固有の条件を追加するPRを検出し、許可なくマージできないゲートを規定。機械検出だけで意味的な専用分岐は完全に防げないため人手の差分レビューを必須とする。
- 例外の許可者、追跡Issue、撤去条件と期限を明文化。

**実コード根拠**: `engine/controllers/communicative-question-flow-controller.js:81` の `/^s006\.communication\./`、`css/dialogue-information.css:165-205` のS006画像パス条件。

### BLOCKER-02 — Communication / UI の**状態遷移表**が足りない

**現状**: モジュール責任はあるが、Goal / Listening / Recognized / Rejected / NoSpeech / Hint / Retry / Accepted / Cancelled / Continued の画面表示とボタン許可、2行/3行寸法の遷移・優先順位が未確定。

**変更要求**:
- 入力イベント × 現在状態 → 次状態、表示するGoal/認識結果/日本語フィードバック/ピコヒント/操作ボタン、2行約100.2pxまたは3行140px、Audio/Speech命令を**1枚の状態遷移表**で定義。
- 「認識できたが不正解」なら、ユーザーの実際の認識結果と `〜と聞こえたよ。` を表示する。無音/認識失敗では架空の認識結果を表示しない。3行表示の適用条件を文章ではなくテスト可能な値として定義。
- 3段ピコサポート 1→2→3→3、次問で0、Goal常時表示、テキスト入力fallback禁止。各段の文言はStoryデータで異なってよいが、**段階1に英語のヒントを含める/含めない**は承認仕様に照合して一貫した審査基準を作る。旧データの存在だけで正解としない。
- S006専用ステータスを取り除いたときにS005/S006/S007が同じ状態機械を使う回帰ケースを定義。

**実コード根拠**: `communicative-question-flow-controller.js:80-147`、`communicative-question-presenter.js:121-137`、`dialog-manager.js:127-142`、`dialogue-information.css:87-90,155-169`。

### BLOCKER-03 — 旧コードを**削除しきったこと**の証明が不足

**現状**: 書換/統合/削除候補は列挙されたが、エントリーポイントやランタイムの依存閉包をどのように検査するか、重複した旧APIの残留をどう阻止するかが抽象的。

**変更要求**:
- 各モジュールの移行表に `旧エントリー → 新エントリー → 移行完了条件 → 削除対象ファイル/関数 → 削除を証明する検査` を定義。
- 新旧経路の比較は**別ビルド**で行い、Productionの実行経路に二重登録/フォールバックを残さない。
- 互換層は対象（例: Save）と所有者・削除条件・存続期間を限定し、テスト成功だけでなく実際の参照箇所がゼロになった証拠を提出。
- 行数削減は合格条件にしない。責任分離、到達不能旧経路の撤去、二重実行の防止を条件とする。

**根拠**: 現行 `audio-manager.js` 3,879行の再生・音量復帰と複数のTrace/Diagnosticの同居。撤去可能性は依存調査前には断定不可。

### BLOCKER-04 — Audio/Speechのライフサイクル契約を検証可能にする

**現状**: 所有者とAttempt IDは記載されているが、マイク・音量・タップ・拒否・取消・再試行・遅延イベントの時系列と境界が未確定。

**変更要求**:
- イベントごとに状態、所有者、再入可能性、取消処理、Audio復帰の冪等性を定義するシーケンス表/図を設ける。
- iPhone正常Reference（Story S002〜S004、Battle m004）を基準に、初回タップ、Speechモード移行、認識結果/無音、マイク解放、BGM duck/restore、Voice再生を比較。
- 既知iPhoneの不安定経路は直ったと宣言しない。新たな原因調査を再開せず、現在の仕様差分と回帰を記録する。

### BLOCKER-05 — CIの**失敗条件と移行例外**を具体化する

**現状**: 受入基準に「共通コード/CSSのGit blob一致」はあるが、レビュー運用/CI gateが曖昧。現行Production自体がStory固有分岐を含むため、単純な全文grepは移行中ずっと失敗する。

**変更要求**:
- 新共通エンジン/新Storyパッケージを対象とするディレクトリとファイル種別、baseline、例外管理を定義する。
- スキーマ検証、禁止実行コード、Story ID/画像URL判定、参照切れ、未承認フラグ、機能カタログ外ステップ、旧経路二重登録など具体的なFAILを列挙。
- 新規Story追加テスト時の許可差分（storyデータ・素材・登録・そのStoryのテストのみ）と、比較するblob SHAを定義。CI status requiredの設定可否はGitHub運用権限も確認し、未設定なら「マージ自動阻止可能」と宣言しない。

### BLOCKER-06 — 作品全体への移行範囲と認定区分を明確化する

**変更要求**:
- S001〜S007に加え、st004、Morning、Camp、m001〜m004、Audio/Saveの依存と互換性を移行完了チェックリストへ展開。
- S005のStory呼び出しはProduction固定SHAの `engine/stories/S005.js:57,59,62,64,65,70,111,113,119,123,146,191` に**12箇所**。これは「正式な11問という承認仕様」を覆す証明ではない。正規の採用問題は差分を裁定してから移植し、既存の12件を無条件に正としない。
- 独立QAが持つ期待値（出典・版）とPMの確認結果を分離。QA未実施/実機未実施は明確にHOLD。100パッケージ登録試験は「100話のすべての将来演出を保証する」証明ではないと明記。
